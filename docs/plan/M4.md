# M4 — PagedAttention：从固定 slot 到分页 KV Cache

> **状态**：✅ 完成（2026-08-11，tag: `m4/paged-attention`）
> **依赖**：M3 — Continuous Batching
> **主层**：L2 Memory
> **知识文档**：[m4-paged-attention.md](../knowledge/m4-paged-attention.md)
> **任务卡目录**：[M4-archive/](../tasks/M4-archive/)

---

## 0. TL;DR

M3 已经解决了多请求如何在 decode iteration 边界重新组 batch，但 KV Cache 仍是固定 slot：每个 running 请求独占一个 `[max_seq_len]` 长度的连续物理空间。M4 要把这个连续空间改成分页管理：请求看到的是连续逻辑 token，底层映射到一组不连续的物理 block。

M4 的目标不是追求 vLLM 级性能，而是手写一个**可读、可测、可解释的 PyTorch 伪版 PagedAttention**，为 M5 Prefix Cache 和 M9 Triton kernel 打地基。

### 设计原则（基于 vLLM V1 研究后的调整）

原 M4 计划包含 Copy-on-Write（CoW），基于 vLLM V0 的 fork 模型。研究 vLLM V1 后调整：

- **M4 不含 CoW**：beam search 不在引擎内 fork，在上层以独立请求方式实现（vLLM V1 做法）
- **ref_count 保留**：为 M5 prefix caching 预留基础设施
- **BlockPool 保持纯元数据**：不耦合 Sequence/RequestState

## 1. 背景：M3 fixed-slot 的问题

M3 的 `BatchedKVCache` 布局：

```text
layers[layer].k: [max_num_slots, n_kv_heads, max_seq_len, head_dim]
```

这很直观，但有三个问题：

| 问题 | M3 表现 | M4 目标 |
|---|---|---|
| 单请求内部碎片 | 每个请求预留 `max_seq_len`，短请求也占满一个 slot | 只按实际长度分配 block，浪费最多一个 block |
| 多请求并发数低 | 按 `max_seq_len` 预留 → 并发数 = 总空间 / max_seq_len | 按需分配 → 并发数 = 总空间 / 平均实际长度，提升数倍 |
| 无跨请求共享 | 两个请求即使 prompt 相同，也各自占一份 KV | 通过 block table + ref_count 为 M5 prefix cache 准备 |

vLLM 的 PagedAttention 论文/博客指出，传统 KV 管理会因碎片和过度预留浪费 60%–80% 显存；PagedAttention 将每个序列的 KV 切成固定大小 block，连续逻辑块映射到非连续物理块，浪费只发生在最后一个 block，实践中低于 4%。

**M4 收益拆解**：

- **单请求**：减少内部碎片。原来浪费 `max_seq_len - actual_len`，现在最多浪费 `block_size - 1` 个 token。
- **多请求**：提高并发数（这是 PagedAttention 论文的核心卖点）。原来按 max_seq_len 预留，现在按需分配，同样的 GPU 能塞进更多并发请求，吞吐直接提升。
- **M5 进一步**：相同前缀的请求共享 block，连重复计算都省了（M4 不含此能力，需 M5 prefix caching）。

## 2. 目标与非目标

### 2.1 目标

| 能力 | M4 是否做 | 说明 |
|---|---|---|
| 物理 KV block 池 | ✅ | `[num_blocks, block_size, n_kv_heads, head_dim]` |

| ref_count | ✅ | 物理 block 引用计数（为 M5 预留） |

| 正确性验证 | ✅ | fixed-slot vs paged token/logits 对齐 |

| 不做 | 原因 | 后续 |
|---|---|---|
| Copy-on-Write | 引擎内不 fork，beam search 在上层做独立请求（学 vLLM V1） | M5（partial hit CoW） |

### 3.3 逻辑地址到物理地址

给定请求的 token 位置 `pos`：


### 3.4 核心代码

#### BlockPool（M4 版，无 CoW）

```python
from collections import deque
from dataclasses import dataclass, field


@dataclass
class Block:
    """物理 block 元数据。"""
    block_id: int
    ref_count: int = 0
    # M5 新增字段（M4 不使用，预留给 prefix caching）
    hash: int = -1
    token_ids: list[int] = field(default_factory=list)


class BlockPool:
    """物理 block 的分配与引用计数管理。

    只管理元数据（哪个 block 空闲、被引用几次），不持有 K/V tensor。
    M4 阶段只做基本的 allocate/free/ref_count。
    M5 阶段升级为 BlockPool，加入 hash 索引和 prefix caching。
    """

    def __init__(self, num_blocks: int, block_size: int) -> None:
        self.num_blocks = num_blocks
        self.block_size = block_size
        self.blocks: list[Block] = [Block(block_id=i) for i in range(num_blocks)]
        self.free_block_ids: deque[int] = deque(range(num_blocks))

    def allocate(self) -> int:
        """分配一个空闲 block，ref_count 置为 1。"""
        if not self.free_block_ids:
            raise RuntimeError("No free blocks available")
        block_id = self.free_block_ids.popleft()
        self.blocks[block_id].ref_count = 1
        return block_id

    def free(self, block_id: int) -> None:
        """释放一个 block（ref_count 减 1，为 0 时归还空闲池）。"""
        self.dec_ref(block_id)

    def inc_ref(self, block_id: int) -> None:
        """增加引用计数（M5 prefix cache 命中时调用）。"""
        self.blocks[block_id].ref_count += 1

    def dec_ref(self, block_id: int) -> None:
        """减少引用计数。降为 0 时自动归还空闲池。"""
        block = self.blocks[block_id]
        assert block.ref_count > 0, f"Block {block_id} ref_count already 0"
        block.ref_count -= 1
        if block.ref_count == 0:
            self.free_block_ids.append(block_id)

    def can_allocate(self, num_blocks: int) -> bool:
        """检查是否有足够空闲 block。"""
        return len(self.free_block_ids) >= num_blocks

    @property
    def num_free_blocks(self) -> int:
        return len(self.free_block_ids)
```

#### BlockTable

```python
@dataclass
class BlockTable:
    """单个请求的逻辑 block 到物理 block 的映射。"""
    request_id: str
    block_ids: list[int]       # logical_block_idx -> physical_block_id
    seq_len: int = 0           # 当前有效 token 数
    block_size: int = 16       # 每个 block 的 token 容量

    @property
    def num_blocks(self) -> int:
        return len(self.block_ids)

    @property
    def num_full_blocks(self) -> int:
        return self.seq_len // self.block_size

    @property
    def last_block_offset(self) -> int:
        """最后一个 block 中已用的 token 数。"""
        return self.seq_len % self.block_size

    def needs_new_block(self) -> bool:
        """追加一个 token 时是否需要分配新 block。"""
        return self.seq_len % self.block_size == 0 and self.seq_len > 0

    def position_to_block(self, pos: int) -> tuple[int, int]:
        """逻辑位置 -> (physical_block_id, block_offset)。"""
        logical_block = pos // self.block_size
        block_offset = pos % self.block_size
        return self.block_ids[logical_block], block_offset
```

#### PagedKVCache

```python
from dataclasses import dataclass
import torch
from inferlite.config import ModelConfig
from inferlite.cache.block_pool import BlockPool


@dataclass
class PagedLayerKVCache:
    """单层 paged KV 数据容器。
    k/v shape: [num_blocks, block_size, n_kv_heads, head_dim]
    """
    k: torch.Tensor
    v: torch.Tensor


class PagedKVCache:
    """分页 KV Cache。

    与 M3 BatchedKVCache 的区别：
      - M3: slot 维，每个请求独占 [max_seq_len] 连续空间
      - M4: block 维，每个请求通过 block_table 映射到多个不连续 block
    """

    def __init__(
        self,
        layers: list[PagedLayerKVCache],
        block_pool: BlockPool,
        block_size: int,
    ) -> None:
        self.layers = layers
        self.block_pool = block_pool
        self.block_size = block_size
        self.block_tables: dict[str, BlockTable] = {}

    @classmethod
    def from_config(
        cls, config: ModelConfig, num_blocks: int, block_size: int,
        dtype: torch.dtype, device: torch.device | str,
    ) -> "PagedKVCache":
        block_pool = BlockPool(num_blocks, block_size)
        layers = []
        for _ in range(config.num_hidden_layers):
            k = torch.empty(
                num_blocks, block_size,
                config.num_key_value_heads, config.head_dim,
                dtype=dtype, device=device,
            )
            v = torch.empty_like(k)
            layers.append(PagedLayerKVCache(k=k, v=v))
        return cls(layers, block_pool, block_size)

    # ── 请求生命周期 ──

    def allocate_request(self, request_id: str, prompt_len: int) -> None:
        """为新请求分配 block table。"""
        num_blocks = (prompt_len + self.block_size - 1) // self.block_size
        block_ids = [self.block_pool.allocate() for _ in range(num_blocks)]
        self.block_tables[request_id] = BlockTable(
            request_id=request_id, block_ids=block_ids,
            seq_len=prompt_len, block_size=self.block_size,
        )

    def free_request(self, request_id: str) -> None:
        """释放请求的所有 block。"""
        table = self.block_tables.pop(request_id)
        for block_id in table.block_ids:
            self.block_pool.free(block_id)

    def may_append_block(self, request_id: str) -> None:
        """decode 追加 token 时，如果需要新 block 则分配。"""
        table = self.block_tables[request_id]
        if table.needs_new_block():
            new_block = self.block_pool.allocate()
            table.block_ids.append(new_block)
        table.seq_len += 1

    # ── KV 读写 ──

    def write_prefill(self, layer_idx: int, request_id: str,
                      k: torch.Tensor, v: torch.Tensor) -> None:
        """prefill 写入：k/v shape [n_kv_heads, prompt_len, head_dim]。"""
        table = self.block_tables[request_id]
        layer = self.layers[layer_idx]
        for pos in range(k.shape[1]):
            block_id, offset = table.position_to_block(pos)
            layer.k[block_id, offset] = k[:, pos, :]
            layer.v[block_id, offset] = v[:, pos, :]

    def write_decode(self, layer_idx: int, request_id: str,
                     k: torch.Tensor, v: torch.Tensor) -> None:
        """decode 写入：k/v shape [n_kv_heads, 1, head_dim]。"""
        table = self.block_tables[request_id]
        layer = self.layers[layer_idx]
        pos = table.seq_len - 1
        block_id, offset = table.position_to_block(pos)
        layer.k[block_id, offset] = k[:, 0, :]
        layer.v[block_id, offset] = v[:, 0, :]

    # ── Attention 读取（gather 伪版）──

    def gather_kv(self, layer_idx: int, request_id: str
                   ) -> tuple[torch.Tensor, torch.Tensor]:
        """按 block_table gather 出连续 KV。
        返回 k/v shape: [n_kv_heads, seq_len, head_dim]
        """
        table = self.block_tables[request_id]
        layer = self.layers[layer_idx]
        k_parts, v_parts = [], []
        for i, block_id in enumerate(table.block_ids):
            start = i * self.block_size
            end = min(start + self.block_size, table.seq_len)
            k_parts.append(layer.k[block_id, :end - start])
            v_parts.append(layer.v[block_id, :end - start])
        k = torch.cat(k_parts, dim=0)
        v = torch.cat(v_parts, dim=0)
        return k.transpose(0, 1), v.transpose(0, 1)
```

### 3.5 M4 与 M3 的接口关系

M3 decode 使用：

```python
cache_slots = torch.tensor([req.slot_id for req in running])
cache_positions = cache.seq_lens[cache_slots]
model(..., kv_cache=cache, cache_slots=cache_slots, cache_positions=cache_positions)
```

M4 改成：

```python
request_ids = [req.request_id for req in running]
cache_positions = paged_cache.positions(request_ids)
block_tables = paged_cache.block_tables(request_ids)
model(..., kv_cache=paged_cache, request_ids=request_ids, cache_positions=cache_positions)
```

## 7. ADR 决策

### ADR-01：M4 新建 `PagedKVCache`，不修改 `BatchedKVCache`

**Context**：M3 的 `BatchedKVCache` 已经稳定，用于 fixed-slot continuous batching。直接改会破坏 M3 回归。

**Decision**：新建 `inferlite/cache/paged_kv_cache.py`，提供 `PagedKVCache` / `PagedLayerKVCache` / `BlockPool` / `BlockTable`。M3 代码保留，M4 通过可选参数或新入口启用 paged 路径。

**Consequences**：
- ✅ M3 fixed-slot 可作为 oracle 做正确性对比。
- ✅ 回滚简单。
- ❌ attention/batch_core 需要类型分派。

### ADR-02：M4 用 PyTorch gather 伪版，不写 Triton kernel

**Context**：vLLM/nano-vllm 使用 Triton/FlashAttention 直接按 block_table 读 KV；Mac/MPS 环境不适合。

**Decision**：M4 每步先按 block table gather 成临时连续 KV，再复用已有 attention 计算。

**Consequences**：
- ✅ 可读、可测、设备兼容。
- ✅ logits/token 等价容易验证。
- ❌ 性能可能比 M3 更慢；接受，M9 再 kernel 化。

### ADR-03：block_size 默认选 16 或 32

**Context**：nano-vllm 默认 `block_size=256`，适合生产吞吐，但不利于单测覆盖跨 block 场景。

**Decision**：M4 默认 `block_size=16` 或 `32`，让短 prompt 也能跨 block，测试更容易发现映射 bug。

**Consequences**：
- ✅ 单测更有效。
- ❌ metadata 相对开销更大；教学版接受。

### ADR-04：M4 不含 CoW，ref_count 为 M5 预留

**Context**：原计划 M4 做 ref_count + Copy-on-Write。研究 vLLM V1 后发现，V1 的 beam search 不在引擎内 fork，而是在上层以独立请求方式实现，prefix caching 自动处理共享。

**Decision**：M4 只实现 allocate/free/ref_count，不做 CoW。ref_count 为 M5 prefix caching 预留。

**Consequences**：
- ✅ M4 更简洁，边界更清楚。
- ✅ M5 可直接在 BlockPool 基础上升级。
- ❌ M4 中无法测试 block 共享场景（留 M5）。

### ADR-05：M4 暂不做 chunked prefill

**Context**：nano-vllm scheduler 已有 token budget/chunked prefill；M4 目标是 L2 Memory，不是 L3 调度策略。

**Decision**：保留 M3 的逐条 prefill + batched decode，只有底层 KV 存储从 slot 改成 paged。

**Consequences**：
- ✅ 变量少，能清楚验证 paging 本身。
- ❌ 长 prompt prefill 阻塞 decode 的问题不解决，留 M10。

### ADR-06：M4 后置整理 — 对齐 vLLM V1 架构

**Context**：T5/T6 完成后暴露两个架构问题：(1) `batch_core.py` 和 `paged_core.py` 主循环 80% 重复；(2) 模型链穿透 9-12 个 cache 参数，4 路 if/elif 分叉。与 vLLM V1 对比发现 6 个 diff 中 5 个是不必要的。

**Decision**：在 M4 Docs/Tag 前插入一个架构对齐任务（合并原 T7+T8）：
- **T7** vLLM V1 Alignment：引入 `ForwardContext` context manager + `CacheAdapter` Protocol + `bind_kv_cache`，统一 engine loop，拆分 `GQAAttention` 为 `Qwen3Attention` + `Attention`，瘦身模型链到 `(input_ids, positions)` 2 参数调用。
- Docs/Tag 顺延为 T8。

**Consequences**：
- ✅ engine loop 统一，M5 只需新增 `PrefixCacheAdapter` 即可接入。
- ✅ model forward 2 参数，与 vLLM V1 对齐。
- ✅ `Attention.forward` 回到 1 条主路径，cache 通过 `bind_kv_cache` 绑定。
- ✅ M3 统一为 batched prefill，消除逐条 prefill 的历史包袱。
- ❌ M1/M2 的 FakeModel 需要适配新 Protocol。

---



| 风险 | 决策 |
|---|---|
| PyTorch 伪版性能更慢 | 接受；M4 是机制教学，性能留 M9 |
| block table 接口污染 M3 | 通过单独 `PagedKVCache` 类型分派，尽量不破坏 `BatchedKVCache` |
| block_size 选多大 | 默认 16 或 32，便于单测跨 block；不沿用 nano-vllm 的 256 |
| M4 与 M5 边界不清 | M4 做分页机制 + ref_count，不做 hash prefix lookup；M5 做 prefix cache policy |
| Attention 主流程继续膨胀 | T7 对齐 vLLM V1：ForwardContext + CacheAdapter + 统一 loop + 模型链瘦身；M5/M9 不再直接往 `Attention.forward` 堆分支 |

## 9. 与 vLLM V1 / nano-vllm 的关系

```text
vLLM V1
  = 生产级 PagedAttention + prefix caching + LRU eviction
  + SWA/MLA/spec decode + serving + scheduler + kernel + 多 GPU

nano-vllm / MinivLLM
  = 小型 CUDA 教学版 vLLM V0，保留 prefix caching 但无 CoW

inferlite M4
  = 纯 PyTorch / Mac 友好的 PagedAttention 机制教学版
    只解决 block table + ref_count + paged gather 正确性
    不含 CoW、prefix caching（M5）、chunked prefill（M10）
```
