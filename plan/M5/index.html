    M5 — Prefix Caching：相同前缀复用已计算的 KV block#

    状态：✅ 完成（tag: m5/prefix-caching，2026-08-19） 依赖：M4 — PagedAttention ✅ 主层：L2 Memory 对齐：vLLM V1 BlockPool + SingleTypeKVCacheManager 任务卡目录：M5-archive/

    0. TL;DR#

    M4 实现了 block 分页的 KV Cache 管理，但每个请求的 block 都是独立分配的，即使两个请求有完全相同的 prompt 前缀，也会各自计算一遍 KV。M5 引入 prefix caching：对填满的 block 计算 chain hash，新请求到来时查 hash 命中，直接复用已缓存的 block 和对应的 KV 数据，跳过重复 prefill。

    核心机制（对齐 vLLM V1）#

    • chain hash：满 block 计算链式 hash（hash = f(prefix_hash, token_ids)），保证不同位置相同 token 产生不同 hash
    • LRU 淘汰：free 时有 hash 的 block 进 LRU 队列（保留等复用），无 hash 的直接归还 free pool；allocate 时优先 free pool，不够再淘汰 LRU
    • touch()：cache 命中时 ref_count++ + 从 LRU 移除
    • partial hit CoW：shared block 需要写入时，拷贝独占副本 + hash 迁移
    • 跳过 prefill：命中 N 个 block → 只 prefill 剩余 token

    1. 背景：M4 的问题#

    请求 A: prompt = [t0, t1, ..., t99, t100]
请求 B: prompt = [t0, t1, ..., t99, t200]

M4 行为：
  A 计算 KV for [t0..t100]   → 占用 block_0, block_1, ...
  B 计算 KV for [t0..t200]   → 占用 block_5, block_6, ...  (完全重新计算)

M5 目标：
  A 计算 KV for [t0..t100]   → 占用 block_0, block_1, ...  并注册 hash
  B 到来时查 hash 命中 [t0..t99] → 复用 block_0, block_1, ...
    只需计算 [t200] 这一个新 token 的 KV

    3. 核心设计#

    3.1 BlockPool 升级（对齐 vLLM V1 BlockPool）#

    M4 BlockPool (85L):
  Block(block_id, ref_count)
  free_block_ids: deque
  allocate() / free() / inc_ref() / dec_ref()

M5 BlockPool (~200L):
  Block(block_id, ref_count, hash, token_ids)
  free_block_ids: deque                    # 真正空闲的 block
  cached_block_lru: OrderedDict            # ref=0 有 hash 的 block（LRU）
  hash_to_block_id: dict[int, int]         # hash → block_id
  compute_hash() / touch() / hash_blocks()
  can_allocate(token_ids) → num_cached
  allocate_with_cache(token_ids, cached) → block_ids

    3.2 LRU 淘汰策略#

    free(block_id):
  ref_count -= 1
  if ref_count == 0:
    if block.hash != -1:
      cached_block_lru[block_id] = None   # 有 hash → LRU 队尾（保留等复用）
    else:
      free_block_ids.append(block_id)      # 无 hash → 直接归还

allocate() 需要新 block:
  if free_block_ids:
    return free_block_ids.popleft()
  elif cached_block_lru:
    block_id, _ = cached_block_lru.popitem(last=False)  # 淘汰最久未用
    reset_hash(block_id)
    return block_id
  else:
    raise RuntimeError

    3.3 Prefix Cache 命中流程#

    新请求 prompt = [t0, t1, ..., t47], block_size = 16

can_allocate(token_ids):
  h = -1
  block 0: tokens [t0..t15] → h = hash([t0..t15], -1)
    → hash_to_block_id.get(h) = block_3 → 命中！num_cached=1
  block 1: tokens [t16..t31] → h = hash([t16..t31], h_prev)
    → hash_to_block_id.get(h) = block_7 → 命中！num_cached=2
  block 2: tokens [t32..t47] → h = hash([t32..t47], h_prev)
    → hash_to_block_id.get(h) = -1 → 未命中，停止

allocate_with_cache(token_ids, num_cached=2):
  touch(block_3) → ref++ + LRU remove
  touch(block_7) → ref++ + LRU remove
  allocate() → block_12（新 block）
  block_table = [3, 7, 12]

prefill:
  skip_tokens = 2 * 16 = 32
  只 prefill [t32..t47] → scatter 到 block_12
  AttentionMetadata.seq_lens = [48]（包含 cached tokens）

    3.4 Partial Hit CoW（对齐 vLLM V1 move_block_hashes）#

    请求 A 和 B 共享 block_3（ref_count=2）
A 的 decode 追加 token 到 block_3 → 需要 CoW：

cow_if_shared(A, block_idx=0):
  old = block_3 (ref=2)
  new = allocate() → block_15
  copy KV: layer.k[15] = layer.k[3].clone()
  migrate hash: hash_to_block_id[h] = 15
  dec_ref(3) → ref=1（B 仍持有）
  A.block_table[0] = 15
  A 继续写入 block_15（独占）

    7. ADR#

    ADR-01：OrderedDict 实现 LRU#

    Context：LRU 需要 O(1) 的 touch（move to end）和 popitem（evict front）。 Decision：collections.OrderedDict，内部双向链表 + dict。 Consequences：代码最简，性能等价手写 LRU。

    ADR-02：chain hash 保证位置唯一性#

    Context：相同 token 序列在不同位置应有不同 hash。 Decision：hash = xxhash64(prefix_hash || token_ids)。 Consequences：前缀匹配天然支持链式 hash；不能匹配后缀。

    ADR-03：同步 CoW#

    Context：vLLM V1 的 _pending_cow_copies 支持异步 CoW 批量执行。 Decision：教学版同步执行，写入前立即 CoW。 Consequences：更简单，性能可接受。

    ADR-04：通过 CacheAdapter 接入（不污染 attention）#

    Context：M4-T7 已建好 CacheAdapter Protocol + ForwardContext 边界。 Decision：prefix cache 逻辑全部在 BlockPool / PagedCacheAdapter / loop.py。 Consequences：attention 主流程不变，M9 kernel 替换不受影响。

    ADR-05：LRU 独立淘汰，不处理孤儿 block#

    Context：prefix chain 中多个 block 有前缀依赖（A→B→C），淘汰 A 后 B、C 变成"孤儿"——仍在 LRU 中但永远无法被 chain hash 命中。 Decision：M5 不做级联淘汰，每个 block 独立进入/离开 LRU。孤儿 block 等待 LRU 自然淘汰。 Consequences： - 实现简单，不需要树结构 - 孤儿 block 临时浪费缓存空间，但不影响正确性 - vLLM V1 用 BlockHashToBlockMap 树结构实现父→子级联淘汰，是更优方案 - 后续 M6+ 可考虑引入简单 tree structure 优化
